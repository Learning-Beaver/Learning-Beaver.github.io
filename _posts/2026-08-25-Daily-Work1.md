# MariaDB 11.4 폐쇄망 설치 작업 정리

> 온라인 서버에서 오프라인 번들을 제작·검증한 뒤, 폐쇄망(신규) 서버에 재현 설치한 전 과정과 시행착오 기록

---

## 1. 개요

| 항목 | 내용 |
|---|---|
| 설치 대상 | MariaDB 11.4.0-preview (bintar-linux-systemd-x86_64) |
| 설치 방식 | 바이너리 타르볼 (RPM 아님) |
| 설치 경로 | `/data/mariadb/11.4` |
| 포트 | 33306 (비표준) |
| 구동 계정 | `mysql` (nologin 시스템 계정) |
| 번들 경로 | `/data/offline/{rpms, tarball, conf, python311}` |
| 번들 제작 환경 | Rocky Linux 9.7 / Rocky Linux 9.5 (온라인) |
| 최종 설치 환경 | Rocky Linux 9.5 (폐쇄망) — **버전 차이가 다수 문제의 원인** |
| SELinux | Enforcing |


## 2. 작업 순서 및 문제·해결 기록

### Phase 0. 사전 결정 사항

- 경로를 `/data/mariadb/4.11`로 잡았다가 버전(11.4)과 뒤바뀐 것을 발견 → **`/data/mariadb/11.4`로 정정**
- `11.4.0-preview`는 GA가 아닌 프리뷰 빌드임을 확인. 실서비스라면 11.4.x GA 권장 (절차는 동일)

### Phase 1. 타르볼 전개 및 의존성 확인

#### 작업 내용

```bash
mkdir -p /data/mariadb/11.4
tar -xzf mariadb-11.4.0-preview-*.tar.gz -C /data/mariadb/11.4 --strip-components=1
```

- `--strip-components=1` 필수 (없으면 한 겹 더 들어간 경로가 됨)

#### 문제 1: 클라이언트 바이너리 라이브러리 누락

```
ldd /data/mariadb/11.4/bin/mariadb
    libncurses.so.5 => not found
    libtinfo.so.5 => not found
```

- **원인**: 타르볼이 ncurses 5 기준으로 빌드됨. Rocky 9는 ncurses 6.x만 제공
- 서버 데몬(`mariadbd`)은 영향 없음. CLI(`mariadb`, `mysql`)만 실행 불가

#### 문제 2: `dnf provides`로 패키지를 못 찾음

```
dnf provides '*/libtinfo.so.5'   → 일치되는 점을 찾지 못했습니다
```

- **원인**: `ncurses-compat-libs`는 RHEL 8에서 deprecated, **RHEL 9 base 리포에서 제거됨. EPEL 9에만 존재**
- **해결**: `dnf install -y epel-release` 후 EPEL에서 다운로드

#### 문제 3: 전수 검사에서 플러그인 의존성 추가 발견

```bash
ldd bin/* lib/plugin/*.so | grep 'not found'
```

| 누락 라이브러리 | 대상 | 해결 패키지 | 비고 |
|---|---|---|---|
| `libncurses.so.5`, `libtinfo.so.5` | mariadb, mysql CLI | `ncurses-compat-libs` (EPEL) | 필수 |
| `libodbc.so.2` | ha_connect.so | `unixODBC` | 선택 (CONNECT 엔진) |
| `libJudy.so.1` | ha_oqgraph.so | `Judy` (EPEL) | 선택 (OQGraph 엔진) |

> **교훈**: 바이너리 하나만 보지 말고 `bin/*` + `lib/plugin/*.so` 전수 검사 후 번들을 확정할 것

### Phase 2. 오프라인 번들 제작

#### 작업 내용

```bash
dnf download --resolve --alldeps --destdir=/data/offline/rpms <패키지들>
createrepo_c /data/offline/rpms/
```

- `dnf install --downloadonly`는 **이미 설치된 의존성을 건너뛰므로 사용 금지**. 반드시 `dnf download --resolve --alldeps` 사용
- 패키지 추가/삭제 시마다 `createrepo_c --update rpms/` 재실행 필수 (빼먹으면 폐쇄망에서 새 RPM이 안 보임)

#### 시행착오

| 문제 | 원인 / 해결 |
|---|---|
| `createrepo_c: 명령어를 찾을 수 없음` (2회 발생) | 리포 생성 도구 자체가 미설치. **번들에도 `createrepo_c` RPM 포함**해 폐쇄망에서 재생성 가능하게 함 |
| `conf/` 디렉토리 부재 | 안내만 되고 실제 생성 명령을 실행하지 않았음. my.cnf, systemd 유닛, repo 파일 작성 |
| 번들 위치를 `/opt` 기준으로 안내했으나 실제는 `/data/offline` | repo 파일의 `baseurl=file:///data/offline/rpms` 로 경로 통일. 문서·스크립트 전체 치환 |

#### 검증 원칙 (온라인 서버에서 미리 실전 검증)

```bash
dnf --disablerepo="*" --enablerepo=local-offline install -y <패키지들>
```

- 온라인 서버에서도 **인터넷 리포를 끄고 로컬 리포로만 설치** → 이 과정 자체가 번들 완전성 검증
- 실패하면 부족한 패키지를 추가 수집하고 리포 갱신하는 루프를 반복 → 번들 완성

### Phase 3. 설치 (계정 / 디렉토리 / 초기화)

#### 작업 내용

```bash
groupadd -r mysql
useradd -r -g mysql -s /usr/sbin/nologin -M -d /data/mariadb/11.4 mysql

mkdir -p /data/mariadb/11.4/{data,log,tmp,run}
chown -R mysql:mysql /data/mariadb/11.4
chmod 750 data ; chmod 640 my.cnf

scripts/mariadb-install-db --defaults-file=... --user=mysql --basedir=... --datadir=...
```

- 초기화 성공. `root@localhost`, `mysql@localhost`가 `unix_socket` 인증으로 생성됨
- `/data` 마운트 옵션에 `noexec` 없음 확인 (있으면 bin/ 실행 불가)

### Phase 4. 서비스 기동 — SELinux 차단 (최대 난관)

#### 문제 4: 기동 즉시 실패

```
mariadbd: Could not open required defaults file: /data/mariadb/11.4/my.cnf
Fatal error in defaults handling. Program aborted
```

#### 진단 과정

```bash
sudo -u mysql cat /data/mariadb/11.4/my.cnf   # → 읽기 OK (DAC 통과)
ausearch -m avc -ts recent
# avc: denied { getattr } ... scontext=system_u:system_r:mysqld_t:s0
#                             tcontext=unconfined_u:object_r:default_t:s0
```

- **원인**: 파일 퍼미션(DAC)은 정상이지만 SELinux(MAC)에서 차단
  - 초기화는 root 쉘(`unconfined_t`)로 실행돼 성공했으나
  - 서비스는 `mysqld_t` 도메인으로 구동 → `default_t` 라벨 파일 접근 불가
- `/data` 는 SELinux 정책이 모르는 경로라 모든 파일이 `default_t` 상태였음

#### 해결: 포트 + 파일 컨텍스트 전체 라벨링

```bash
semanage port -a -t mysqld_port_t -p tcp 33306          # 비표준 포트 등록

semanage fcontext -a -t mysqld_etc_t     "/data/mariadb/11\.4/my\.cnf"
semanage fcontext -a -t mysqld_db_t      "/data/mariadb/11\.4/data(/.*)?"
semanage fcontext -a -t mysqld_log_t     "/data/mariadb/11\.4/log(/.*)?"
semanage fcontext -a -t mysqld_var_run_t "/data/mariadb/11\.4/run(/.*)?"
semanage fcontext -a -t mysqld_tmp_t     "/data/mariadb/11\.4/tmp(/.*)?"
semanage fcontext -a -t mysqld_exec_t    "/data/mariadb/11\.4/bin/mariadbd"
semanage fcontext -a -t bin_t            "/data/mariadb/11\.4/bin(/.*)?"
semanage fcontext -a -t lib_t            "/data/mariadb/11\.4/lib(/.*)?"
semanage fcontext -a -t usr_t            "/data/mariadb/11\.4/share(/.*)?"

restorecon -R /data/mariadb/11.4                        # 실제 적용 (필수!)
```

> **교훈**
> - `semanage`는 규칙 등록만, `restorecon`이 실제 적용 — 세트로 실행할 것
> - DB 초기화 후 새로 생긴 파일에도 `restorecon -R data/` 재실행
> - 비표준 포트(33306)는 `mysqld_port_t` 등록 없이는 바인드 자체가 거부됨
> - `semanage` 명령은 `policycoreutils-python-utils` 패키지 필요 (Rocky 9 minimal 기본 미설치 → 번들 포함)

### Phase 5. 접속 및 계정 체계

#### 문제 5: `mariadb -P 33306 -u root -p` → ERROR 1130

```
Host '127.0.0.1' is not allowed to connect to this MariaDB server
```

- **원인**: `-P` 옵션 → TCP 접속 → 서버는 `root@127.0.0.1`로 인식. 그러나 계정은 `root@localhost`(소켓 전용)뿐
- `skip-name-resolve` 활성화로 127.0.0.1 → localhost 역변환도 안 됨

#### 핵심 개념 정리 (`user@host`)

- `@host`는 **접속해 오는 클라이언트의 위치**. OS 계정명과 무관
- `localhost` = 유닉스 소켓 / `127.0.0.1` = TCP 루프백 → **서로 다른 계정**
- `'%'`는 모든 원격을 의미하지만 **localhost(소켓)는 포함하지 않음** → 로컬용 계정 별도 생성 필요
- 클라이언트에서 `-h localhost -P 33306`은 포트 무시하고 소켓으로 감 → TCP 강제는 `-h 127.0.0.1` 또는 `--protocol=tcp`
- `skip-name-resolve` 상태에서는 호스트명 기반 계정(`@'was01.example.com'`) 사용 불가. IP/IP패턴만 가능
- 매칭은 더 구체적인 host가 우선

#### 계정 구성 결정

```sql
-- root: 소켓 전용, 비밀번호 인증으로 전환 (unix_socket 제거)
ALTER USER 'root'@'localhost' IDENTIFIED VIA mysql_native_password USING PASSWORD('...');

-- 애플리케이션: 전체 대역 (초기 10.0.0.% → 요건 변경으로 전환)
RENAME USER 'appuser'@'10.0.0.%' TO 'appuser'@'%';
GRANT SELECT, INSERT, UPDATE, DELETE ON appdb.* TO 'appuser'@'%';
```

- root의 `unix_socket` 인증 제거 → 항상 비밀번호 요구 (보안 요건)
  - 대가: 비밀번호 분실 시 `--skip-grant-tables` 재기동으로만 복구 가능 → 절차 문서화 필요

#### 문제 6: 일반 OS 계정(bdp)에서 접속 불가

- **원인 후보 2가지**
  1. `~/.my.cnf` 부재로 기본 소켓 경로(`/var/lib/mysql/mysql.sock`)를 찾음
  2. `run/` 디렉토리가 750 + `mysql:mysql` (서비스 `UMask=007`) → mysql 그룹 미소속 계정은 소켓 접근 불가
- **해결**

```bash
usermod -aG mysql bdp            # 재로그인 필요
# bdp 홈에
cat > ~/.my.cnf <<'EOF'
[client]
socket = /data/mariadb/11.4/run/mysql.sock
EOF
```

|---|---|
| 비밀번호 전달 방식 | 환경변수/파일 방식 검토 후 **대화식 입력(read -rsp)으로 확정**. 히스토리·ps·environ 노출 원천 차단 |

### Phase 7. 신규(폐쇄망) 서버 재설치 — 마이너 버전 충돌

> 번들 제작: **Rocky 9.7** / 설치 대상: **Rocky 9.5** — 여기서 문제 집중 발생

#### 문제 7: ncurses 버전 충돌

```
cannot install both ncurses-libs-6.2-12(번들, 9.7) and ncurses-libs-6.2-10(@System, 9.5)
package ncurses-6.2-10 requires ncurses-libs = 6.2-10
```

- **원인**: base 패키지(`ncurses-libs`)를 번들에 넣고 설치 목록에도 포함 → dnf가 최신(6.2-12)을 선택 → 시스템의 `ncurses-6.2-10`이 버전을 고정하고 있어 충돌

#### 시행착오 (해결까지의 우회로)

1. `--releasever=9.5` 재수집 시도 → **404**. mirrorlist는 최신 마이너만 서비스, 구버전은 **vault**로 이관됨
   ```
   baseurl=https://dl.rockylinux.org/vault/rocky/9.5/BaseOS/x86_64/os/
   ```
   (vault repo는 `enabled=0`으로 두고 필요 시에만 활성화 — 온라인 장비 다운그레이드 방지)
2. `--enablerepo=epel` → `알 수 없는 저장소`. EPEL repo id 상이 → 어차피 `Judy`는 이미 수집돼 있어 EPEL 불필요했음
3. vault에서 6.2-10 수집 → 번들에 6.2-10/6.2-12 공존 → **dnf가 여전히 최신을 선택해 동일 충돌**
4. compat 버전 매칭 로직(`ncurses-compat-libs-${시스템버전}`) 시도 → **실패**. `ncurses-compat-libs`는 EPEL 빌드(6.2-8)라 base 버전과 애초에 무관 — 잘못된 접근이었음

#### 최종 해결: "base 패키지는 번들에서 제외" 원칙

```bash
cd /data/offline/rpms
rm -f ncurses-6.2-*.rpm ncurses-base-*.rpm ncurses-libs-*.rpm   # base 패키지 제거
rm -f *.i686.rpm                                                 # 32bit 불필요
rm -rf repodata && createrepo_c rpms/                            # 메타데이터 전체 재생성
```

```bash
# 설치 목록에서도 ncurses-libs 제거
PKGS="libaio numactl-libs libxcrypt-compat policycoreutils-python-utils \
unixODBC Judy ncurses-compat-libs"
```

> **핵심 원칙**: 번들에는 **대상 서버에 기본 설치되어 있지 않은 패키지만** 담는다.
> 기본 패키지(ncurses, glibc 계열 등)를 넣으면 마이너 버전이 다를 때마다 충돌한다.
> `ncurses-compat-libs`(EPEL, 6.2-8)는 버전 독립적이라 9.5/9.7 모두 그대로 설치됨.

### Phase 8. Python 3.11 추가 반입

#### 구성 결정

- MariaDB 번들과 **리포 분리**: `/data/offline/python311/rpms` + 전용 repo 파일
- `python3`(3.9)은 시스템 도구(dnf, semanage, firewall-cmd)가 의존하므로 **절대 교체 금지**. `python3.11` 명령/venv로 사용

#### 문제 8: OpenSSL 버전 충돌 (미해결 → 해결 방향 확정)

9.5 서버에서 설치 시:

```
python3.11-libs-3.11.13-10.el9_8 requires libcrypto.so.3(OPENSSL_3.3.0/3.4.0)
cannot install both openssl-libs-1:3.5.5-6.el9_8 and openssl-libs-1:3.2.2-6.el9_5(@System)
package openssl-1:3.2.2-6.el9_5 from @System requires openssl-libs = 1:3.2.2-6.el9_5
```

- **원인**: 온라인 장비의 리포가 이미 9.8 시점 패키지를 서비스 → 받아온 `python3.11-*-el9_8`이 OpenSSL 3.5(el9_8)를 요구 → 9.5 시스템의 OpenSSL 3.2와 충돌. **ncurses와 동일한 구조의 문제이며, openssl은 pam/cockpit 등 핵심 패키지가 물려 있어 업그레이드 강행 불가**
- **해결 방향**: vault 9.5 리포에서 python3.11 계열을 재수집

```bash
dnf download --resolve --alldeps \
  --disablerepo="*" \
  --enablerepo="vault95-baseos,vault95-appstream,vault95-crb" \
  --destdir=/data/offline/python311/rpms \
  python3.11 python3.11-libs python3.11-pip python3.11-setuptools

# 기존 el9_8 RPM 제거 후 리포 재생성
cd /data/offline/python311/rpms && rm -f python3.11*el9_8*.rpm
cd .. && rm -rf rpms/repodata && createrepo_c rpms/
```

> python3.11은 base(AppStream) 패키지라 "base 제외" 원칙을 적용할 수 없음 →
> 이 경우에는 **대상 마이너 버전(vault)에 맞춰 수집**하는 것이 정답.

## 4. 확립된 원칙 (재사용 체크리스트)

### 번들 제작
- [ ] `dnf download --resolve --alldeps` 사용 (`--downloadonly` 금지)
- [ ] **base 기본 패키지는 번들에서 제외** — 대상에 없는 것만 담기
- [ ] base 계열 패키지가 꼭 필요하면(python3.11 등) **대상 마이너 버전 vault에서 수집**
- [ ] EPEL 패키지(compat-libs, Judy)는 마이너 버전 무관 → 그대로 사용 가능
- [ ] i686 RPM 제거
- [ ] RPM 변경 시마다 `createrepo_c` 재생성 (`--update` 불안하면 repodata 삭제 후 전체 재생성)
- [ ] `createrepo_c` RPM 자체를 번들에 포함
- [ ] `ldd bin/* lib/plugin/*.so` 전수 검사 → `not found` 0건 확인 후 확정
- [ ] 온라인 장비에서 `--disablerepo="*" --enablerepo=local-offline` 으로 실전 설치 검증
- [ ] `env-online.txt` (OS/커널/glibc/openssl 버전) 동봉, sha256 별도 파일로 반입

### 설치
- [ ] 대상 서버 사전 점검: 마이너 버전, `noexec`, SELinux 모드, 포트 선점, 디스크
- [ ] SELinux: 포트(`mysqld_port_t`) + 컨텍스트 9종 + **restorecon** (초기화 후 data/ 재실행)
- [ ] 기동 실패 시 진단 순서: `journalctl` → 에러로그 → `ausearch -m avc`
- [ ] 비밀번호는 대화식 입력만, SQL은 heredoc으로 전달

### 계정/보안
- [ ] `user@host`의 host는 클라이언트 위치. `localhost`(소켓) ≠ `127.0.0.1`(TCP) ≠ `%`(원격)
- [ ] root는 소켓 전용 유지, 원격은 용도별 계정 분리
- [ ] `skip-name-resolve` 환경에서는 IP 기반 계정만 사용
- [ ] 이중 방어: 방화벽(firewalld) + DB 계정 host 제한
